# Технічне завдання (ТЗ) на розробку системи моніторингу VPS/VDS «VPSGuard»

## 1. Загальні положення

### 1.1. Найменування системи

Повне найменування: **VPSGuard — система моніторингу віртуальних серверів (VPS/VDS)**  

Коротке: **VPSGuard**

### 1.2. Призначення документа

Цей документ є технічним завданням (ТЗ) на розробку програмного забезпечення системи VPSGuard. Він визначає вимоги до функціональності, архітектури, інтерфейсів, безпеки та інших аспектів, необхідних для реалізації та впровадження.

### 1.3. Мета створення системи

Система призначена для централізованого моніторингу, аналізу та управління віртуальними серверами (VPS/VDS). Вона забезпечує збір детальних метрик з кожного сервера, їх зберігання, візуалізацію, а також автоматичне сповіщення та виконання дій при виникненні проблем. Основна мета — підвищити надійність, продуктивність і безпеку інфраструктури.

### 1.4. Цільова аудиторія

- Системні адміністратори

- DevOps-інженери

- Хостинг-провайдери

- Власники невеликих та середніх IT-інфраструктур

## 2. Область застосування

Система може використовуватись для:

- Моніторингу одного або декількох VPS/VDS серверів (від 1 до 10 000+).

- Контролю використання ресурсів (CPU, RAM, диск, мережа).

- Виявлення аномалій та прогнозування проблем.

- Автоматичного реагування на інциденти (self-healing).

- Ведення історії та генерації звітів.

- Забезпечення безпеки (виявлення атак, моніторинг логів).

## 3. Вимоги до системи

### 3.1. Функціональні вимоги

#### 3.1.1. Агент (VPSGuard Agent)

Агент встановлюється на кожен моніторований сервер і виконує такі функції:

1. **Збір метрик**:

   - CPU: загальне завантаження, по кожному ядру, частота, температура (якщо доступно через ACPI/sensors).

   - Пам'ять: total/used/free, swap, деталізація за процесами.

   - Диски: використання простору, I/O операції (read/write, IOPS), SMART-дані (для фізичних дисків).

   - Мережа: трафік (rx/tx bytes, packets, errors), швидкість інтерфейсів, активні з'єднання.

   - Температури: CPU, GPU (nvidia-smi), NVMe/SSD (smartctl), материнська плата (sensors).

   - Процеси: топ-N за CPU/RAM, загальна кількість, зомбі-процеси.

   - Служби: статус systemd-сервісів, uptime.

   - Docker (якщо встановлено): статистика контейнерів (CPU%, RAM, мережа, блокові I/O, статус).

   - Безпека: кількість невдалих SSH-спроб, статус брандмауера (UFW/iptables), останні входи.

   - SSL-сертифікати: перевірка терміну дії для локальних доменів.

   - Логи: аналіз вибраних лог-файлів на наявність помилок/патернів.

2. **Передача даних**:

   - Надсилання метрик на центральний сервер через HTTPS (REST API) або WebSocket з інтервалом, що налаштовується (за замовчуванням 30 секунд).

   - Буферизація даних у разі втрати зв'язку (до 24 годин) з подальшою відправкою.

3. **Виконання команд**:

   - Отримання команд від центрального сервера (наприклад, перезапуск служби, виконання скрипта).

   - Виконання команд у пісочниці з обмеженими правами (за замовчуванням — від імені непривілейованого користувача).

   - Повернення результату виконання.

4. **Локальна конфігурація**:

   - Зберігання параметрів підключення (URL сервера, API-ключ) у файлі конфігурації.

   - Оновлення агента через централізовану команду або локально.

5. **Самодіагностика**:

   - Перевірка власного стану, логування помилок.

#### 3.1.2. Центральний сервер (VPSGuard Server)

1. **Прийом даних**:

   - REST API endpoint `POST /api/v1/ingest` для отримання метрик від агентів.

   - WebSocket endpoint для постійного з'єднання (опційно).

2. **Аутентифікація та авторизація**:

   - Кожен агент має унікальний API-ключ, прив'язаний до сервера.

   - Користувачі (адміністратори, оператори, глядачі) з ролями та правами доступу.

3. **Зберігання даних**:

   - Метрики часу зберігаються у часовій базі даних (InfluxDB або TimescaleDB).

   - Конфігураційні дані (користувачі, сервери, правила алертів) — у PostgreSQL.

   - Кеш та черги — Redis.

4. **Аналіз даних**:

   - Обчислення агрегатів (середнє, максимум, мінімум) за періодами.

   - Виявлення аномалій (алгоритми Isolation Forest, LSTM або порогові правила).

   - Прогнозування (лінійна регресія, ARIMA) для передбачення заповнення диска, трендів навантаження.

5. **Алертинг**:

   - Створення правил алертів на основі порогів, трендів, аномалій, станів.

   - Менеджер алертів з підтримкою станів: firing, acknowledged, resolved.

   - Відправка повідомлень через Telegram, Slack, Email, Webhook.

   - Дедуплікація та групування алертів.

6. **Управління агентами**:

   - Реєстрація нових агентів, збереження інформації про сервери.

   - Відправка команд агентам (через WebSocket або відкладене завдання).

   - Моніторинг стану агентів (heartbeat).

7. **REST API**:

   - Повний CRUD для серверів, правил алертів, користувачів, звітів.

8. **Планувальник завдань**:

   - Виконання автоматичних дій за тригерами (наприклад, перезапуск служби при падінні).

9. **Генерація звітів**:

   - Формування звітів (PDF, CSV) за розкладом або на вимогу.

#### 3.1.3. Веб-дашборд (VPSGuard Dashboard)

1. **Інтерфейс користувача**:

   - Сторінка огляду зі станом усіх серверів.

   - Список серверів з фільтрами, пошуком, групами.

   - Детальна сторінка сервера з графіками (CPU, RAM, Disk I/O, Network) у реальному часі та історією.

   - Перегляд температур, топ процесів, Docker-контейнерів, логів, статусів служб.

   - Управління алертами та правилами.

   - Налаштування користувачів, ролей, інтеграцій.

2. **Графіки**:

   - Використання бібліотек Chart.js/Recharts.

   - Авто-оновлення через WebSocket (затримка 1-2 секунди).

   - Можливість накладання метрик з різних серверів.

3. **Веб-термінал**:

   - Доступ до сервера через xterm.js + WebSocket.

   - Аудит введених команд.

4. **Мобільна адаптація**:

   - PWA або адаптивний дизайн для мобільних пристроїв.

#### 3.1.4. Додаткові функції (обов'язкові для реалізації)

- **Прогнозування**: алерти на основі прогнозу заповнення диску за 3 дні до події.

- **Self-Healing**: автоматичний перезапуск сервісу при його падінні, очищення логів при переповненні диска (з обережністю).

- **Безпековий моніторинг**: виявлення brute-force атак через аналіз SSH логів, сповіщення про нові відкриті порти.

- **SSL-моніторинг**: перевірка терміну дії сертифікатів з алертами за 30, 14, 7, 1 день.

- **Віддалений термінал**: Web SSH.

- **Групування серверів**: створення груп (prod, staging, dev) та масові операції.

### 3.2. Нефункціональні вимоги

#### 3.2.1. Продуктивність

- Агент повинен споживати не більше 1% CPU та 50 MB RAM.

- Центральний сервер повинен обробляти не менше 1000 метрик/сек на одному вузлі.

- Час відповіді API < 200 мс для 95% запитів.

#### 3.2.2. Масштабованість

- Горизонтальне масштабування серверної частини (за балансувальником).

- Шардінг бази даних часових рядів.

- Підтримка до 10 000 агентів.

#### 3.2.3. Надійність

- Втрата зв'язку з агентом не повинна призводити до втрати даних (буферизація).

- Резервне копіювання PostgreSQL та InfluxDB.

- Автоматичне відновлення після збоїв.

#### 3.2.4. Безпека

- Шифрування трафіку між агентом і сервером (TLS 1.2+).

- Зберігання паролів у хешованому вигляді (bcrypt/argon2).

- RBAC з ролями: admin, operator, viewer.

- Обмеження прав агента (виконання команд у sandbox).

- Аудит дій користувачів.

#### 3.2.5. Сумісність

- Агент повинен працювати на основних Linux-дистрибутивах: Ubuntu 20.04+, Debian 11+, CentOS 8+, AlmaLinux, Rocky Linux, Alpine (частково).

- Підтримка Docker для розгортання агента (опційно).

- Дашборд повинен працювати в останніх версіях Chrome, Firefox, Safari, Edge.

#### 3.2.6. Зручність використання

- Інсталяція агента однією командою.

- Інтуїтивно зрозумілий інтерфейс.

- Наявність документації.

## 4. Архітектура системи

### 4.1. Компоненти

- **Агент** (Bash/Python скрипт або Docker-контейнер) — встановлюється на сервер.

- **Центральний сервер** (Node.js/NestJS або Python/FastAPI) — REST API, WebSocket, обробка даних.

- **База даних часових рядів** — InfluxDB 2.x або TimescaleDB.

- **Реляційна БД** — PostgreSQL.

- **Кеш/черга** — Redis.

- **Дашборд** — React + Next.js (або Vue.js), спілкується з API та WebSocket.

### 4.2. Схема взаємодії

Агент збирає метрики → надсилає на сервер через HTTPS → сервер валідує, зберігає в InfluxDB, аналізує → при спрацюванні алерту відправляє повідомлення → дашборд отримує оновлення через WebSocket.
